# 1) What the Canonical Calculator is
 
The Canonical Calculator is a **deterministic computation service** that:
 
 
1. Ingests **birth and configuration facts** (time, place, timezone, system options)
 
2. Produces a **normalized astronomical state** + **derived astrological primitives**
 
3. Emits **machine-usable JSON** with strict versioning, allowing downstream services to operate without recalculating or guessing.
 

 
**Non-negotiable constraint:** LLMs never compute. LLMs interpret **only** canonical outputs.
  
# 2) Why “canonical” matters
 
Without a canonical engine, you get:
 
 
- the same user producing different chart results depending on screen, feature, or prompt
 
- interpretation drift because different modules compute different house cusps/aspect orbs
 
- timing windows shifting silently across releases
 

 
Aethos needs the opposite:
 
 
- **reproducible charts**
 
- **reproducible event windows**
 
- **auditable versioning**
 
- **clear system toggles** (tropical vs sidereal, Whole Sign vs Placidus, ayanamsa choice, etc.)
 

  
# 3) Inputs: facts, not vibes
 
## Required input schema (minimum)
 
### Identity / provenance
 
 
- `subject_id` (UUID)
 
- `name_full` (string; optional)
 
- `birth_source` (“certificate” | “family_memory” | “approx”)
 
- `time_accuracy_minutes` (int, 0–720)
 

 
### Birth data
 
 
- `birth_date` (YYYY-MM-DD)
 
- `birth_time` (HH:MM[:SS])  *(if unknown, must be null and handled explicitly)*
 
- `birth_place`: 
 
  - `lat` (float)
 
  - `lon` (float)
 
  - `place_label` (string)
 

 
 
- `timezone` (IANA string, e.g. `"America/Los_Angeles"`)
 

 
### Configuration toggles (must be explicit)
 
 
- `zodiac_system`: 
 
  - `"tropical"` OR `"sidereal"`
 

 
 
- If sidereal: 
 
  - `ayanamsa` (e.g., `"lahiri"` | `"raman"` | `"fagan_bradley"`)
 

 
 
- `house_system` (for Western): 
 
  - `"whole_sign"` (default)
 
  - optional: `"placidus"`, `"koch"`, `"regiomontanus"` etc.
 

 
 
- `orb_policy` (named policy object; do not hardcode)
 
- `points_enabled` (nodes, chiron, asteroids, etc.)
 

 
### Timing options
 
 
- `include_velocity` (boolean; should be true in canonical output)
 
- `ephemeris`: 
 
  - `provider` = `"swisseph"`
 
  - `swe_version`
 
  - `ephemeris_fileset` (e.g. DE431 subset)
 

 
 

 
**Rule:** every toggle is stored. No implicit defaults in downstream layers.
  
# 4) Outputs: the canonical JSON contract
 
The canonical output must be **normalized**, **complete**, **traceable**, and **cacheable**.
 
## A) Canonical birth record (astronomical truth)
 
This is the root of everything.
 
 
- `birth_local_datetime`
 
- `birth_timezone`
 
- `birth_utc_datetime`
 
- `julian_day`
 
- `delta_t` (if used)
 
- `geo` (lat/lon)
 
- `calc_version` (semver + git hash)
 
- `ephemeris_version` (swisseph + files)
 

 
This ensures reproducibility across years.
 
## B) Western chart primitives (tropical or sidereal)
 
Regardless of interpretation, you must output the raw state.
 
### Planets (all with speed)
 
For each body:
 
 
- `lon` (0–360)
 
- `lat`
 
- `distance`
 
- `speed_lon`
 
- `speed_lat`
 
- `speed_dist`
 
- `retrograde` (derived: speed_lon < 0)
 
- `sign` (derived)
 
- `house` (derived via house system)
 

 
**Why speed matters:** retrogrades, stations, and event-window logic require it.
 
### Angles / houses
 
Depending on system:
 
 
- Whole Sign: 12 houses derived from Asc sign
 
- Quadrant: cusps, MC, ASC computed
 

 
Store:
 
 
- `asc_lon`
 
- `mc_lon`
 
- house cusps if relevant
 
- `houses` array with sign + degrees coverage
 

 
## C) Aspect graph (normalized)
 
Aspects are not prose. They are graph edges with measured separation.
 
Each aspect edge:
 
 
- `body_a`
 
- `body_b`
 
- `aspect_type`
 
- `exact_angle`
 
- `orb`
 
- `applying_or_separating` (derived from speeds)
 
- `strength_score` (optional but useful)
 

 
This becomes the structural input for interpretation.
 
## D) Derived conditions (Hellenistic-friendly)
 
These are computed properties that reduce downstream complexity.
 
Examples:
 
 
- `sect` (day/night chart)
 
- dignity status (domicile/exaltation/detriment/fall)
 
- angularity (angular/succedent/cadent)
 
- house ruler chains
 

 
These are deterministic and can be versioned.

# 11) One important correction (to avoid a trap)
 
In the schemas above I used:
 
 
- `format: date-time` for `birth_local_datetime`.
 

 
Strictly, “local datetime” is *not* a real RFC3339 absolute moment unless it includes an offset. To keep it compliant, you have two strong options:
 
**Option A (recommended):** store local time as *naive* strings:
 
 
- `birth_local_date` (YYYY-MM-DD)
 
- `birth_local_time` (HH:MM:SS)
 
- `birth_timezone` (IANA) …and treat `birth_utc_datetime` as the canonical absolute.
 

 
**Option B:** include local with offset:
 
 
- `birth_local_datetime` like `"1991-11-06T17:43:00-05:00"` plus IANA.
